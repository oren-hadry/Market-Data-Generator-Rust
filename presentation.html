Architecture — Phase 1

(Data)Generator  [ Thread 1: Producer ]
    │  MarketEvent { symbol, side, price, size, id }
    ▼
BooksManager  ──  HashMap<String, OrderBook>  (O(1) symbol lookup)
    │
    ▼
OrderBook (per symbol)
    ├── BookSide [bid]  BTreeMap<OrderedFloat<f64>, BookLevel>  ── O(log N), max 100 levels

    ▼

Key Design Decisions

click ↓ to go through each one

🔢 OrderedFloat<f64> as BTreeMap key
📦 crossbeam bounded(256) replaces hand-rolled SPSC
🔗 Sender<T> instead of std::function callback
🚦 Arc<AtomicBool> for signal-safe shutdown

OrderedFloat<f64>

C++
std::map<double, BookLevel>
compiles — undefined behavior on NaN
Rust
BTreeMap<OrderedFloat<f64>, BookLevel>
f64 has no Ord (NaN) — compiler refuses bare f64
Phase 2 plan: move to i64 fixed-point ticks — integer ALU, no FP comparison at all.

crossbeam bounded(256)

C++
Hand-rolled BoundedSPSCQueue
custom atomic ops, potential UB (on wrong memory ordering)
Rust
crossbeam_channel::bounded(256)
same semantics, battle-tested, zero unsafe, Producer blocks on send() when full → backpressure, no overflow Consumer blocks on recv() when empty

When channel is full → send() blocks the producer → natural backpressure, no extra logic needed.

std::sync::mpsc — can't wait on multiple channels (needed in Phase 2)
tokio::sync::mpsc — requires async runtime; our code is purely sync (std::thread)

Sender<T> as push callback

One channel, multiple writers — bid and ask sides send independently. Sender is Clone + Send, so each gets its own handle to the same queue. 

// engine.rs passes a clone to BooksManager
let manager_tx = tx.clone();

// Each BookSide holds its own clone
let bid_tx = tx.clone();
let ask_tx = tx.clone();

// When ALL senders drop → channel closes → consumer exits
Shutdown sequence: producer loop exits → all senders (original + per-BookSide clones) drop (out of scope) → channel closes → consumer drains remaining, exits cleanly.

Arc<AtomicBool> for Ctrl+C

let running = Arc::new(AtomicBool::new(true));
let r = running.clone();
ctrlc::set_handler(move || { r.store(false, Ordering::SeqCst); })?;
// producer thread: while running.load(Ordering::SeqCst) { ... }
Arc — shared ownership across threads, no dangling references
AtomicBool — race-free store/load, no lock needed

Selected Rate Profiles

ProfileBehaviourUse case
constantFixed rate at base_rateBaseline / unit tests
sineOscillates base_rate ↔ max_rateSimulate market hours
burst5% chance spike to max_rateRecovery from sudden load
rampLinear base → max over 60s, then holdsFind the breaking point
Ramp formula:
rate(t) = base_rate + min(t/60, 1.0) × (max_rate − base_rate)

Surfaces failures at the exact rate threshold — not just "works at 1k, fails at 10k".

FAQ

Q: Won't spin-wait burn 100% CPU when the channel is full?
Yes, by design — minimising latency over power. Mitigation in Phase 2: fall back to yield after N failed spins if CPU budget is constrained.
Q: f64 as map key — precision issues?
C++ silently accepted NaN comparisons. Rust refuses to compile bare f64 as BTreeMap key. OrderedFloat adds defined ordering. Phase 2 moves to i64 fixed-point.
Q: Where does rate control live, and why?
Phase 1: Consumer-side — producer runs at full speed, sink sleeps to match the profile. Keeps OrderBook decoupled from transport; swap profiles without touching book code.
Phase 2: Per-symbol producer — each symbol throttles at the source. Consumer just drains. In both phases, a full channel blocks send() as a natural safety valve.

Phase 4 — True HFT (<1µs)

Memory & Data Structures

→ SPSC ring buffer — crossbeam is MPMC with extra atomics. SPSC has one writer, one reader → no false sharing

→ Flat array instead of BTreeMap — BTreeMap scatters nodes on heap. Contiguous array → CPU fetches several levels per cache line

→ Zero heap allocation on hot path — pre-allocate at startup, no malloc during trading

OS & Network

→ isolcpus + SCHED_FIFO — dedicated cores excluded from OS scheduler. No housekeeping threads, no IRQs, no preemption

→ mmap shared memory — zero-copy, zero syscalls between processes

→ DPDK kernel bypass — send() costs ~1µs in kernel. DPDK writes directly to NIC from userspace

Each change eliminates a specific latency source: false sharing · pointer chasing · scheduler jitter · kernel overhead
